# BeingOS design coverage

Reviewed 21 November 2026 against the [design and phased plan](../DESIGN-AND-PLAN.md). Use the [USB readiness record](USB-READINESS.md) for current work assignments, candidate identity and release decisions. Each row identifies the evidence needed to close that part of the design.

**Evidence levels.** *Guest* means the named behavior passed on a particular virtual disk or overlay. *Host* means it ran on the development Mac. *Source* means an implementation or test exists. *Open* means the evidence required by the design is outstanding. A passing staged image qualifies only the features exercised on it. The ownership table maps the workstreams in each acceptance row to work areas.

**When work can close.** Software gaps below can be prepared, implemented or tested before physical media. Items called *physical* require the actual laptop. Explicitly optional experiments retain their recorded decision or promotion test. Open design commitments stay visible until they pass, or Richard accepts a change of scope. The first development USB is the instrument for Phase 0. Its preparation cannot yield measurements from the MacBook.

## Differences that need an explicit disposition

- The revised design brings Buildroot to the lab before Phases 0 and 1. The stock Debian path can still identify a missing driver. The compact factory geometry and installed capacity calculation serve different purposes. Check the actual selected layout against the 256 GB design before installation.
- The production speech stack is a benchmark decision. The current PocketSphinx/Flite baseline is usable for qualification. Speaker ID, eye-contact attention, acoustic interruption, deliberate vision and procedural chirps have separate acceptance work.
- The earlier standalone Try opens a temporary session directly. A separately staged local menu has an unresolved visible-first-frame test. The release still needs direct screen-driven Try/Install/Restore and installed retention/setup evidence. A RAM-only Try session does not qualify installed guest retention or a restored deletion ledger.
- Model, speech and physical timing estimates in the design remain targets. The Qwen and SQLite defaults, rejected learned routing changes, and deferred optional hosted inference each have their own evidence. No hosted trial is necessary for offline operation.
- The design's nightly consolidation, backups and diagnostic sharing have separate owner controls. Source-backed journal runs, encrypted backups, paired read-only observation and signed updates each demonstrate their own slice. The integrated guest and physical laptop still need to verify overnight eligibility and stop conditions.
- Formal 24-hour face, 48-hour recovery and one-week appliance soaks require dedicated bounded runs and reports. Keep guest and physical measurements distinct. Hardware-dependent exit criteria follow the first physical boot. A decision to defer feasible software changes belongs in the release record.

## Running the virtual organ soak

Start the runner in a foreground terminal against the chosen factory image. It creates a disposable QEMU overlay, enables the guest's ALSA loopback voice service and writes a new JSONL evidence file. The five-minute example exercises the harness.

```sh
python3 -m lab.soak --image out/images/beingos.img --seconds 300 --interval 30
```

After factory boot confirmation, each sample checks an actual brainstem heartbeat and state, local cortex HTTP health, and active/restart counters for the five normally running organs. The final sample must cover the requested duration on both monotonic clocks. Interruptions, unexpected restarts and missed observations produce a failure record. A successful run records the exact image digest, per-service counters and guest cleanup. The opt-in camera and intentional fault injection require their own scenarios. The Phase 2/3 physical frame, audio, crash-recovery and week-long qualification are still outstanding. [Runner](../lab/soak.py) · [Controller tests](../tests/test_soak.py)
